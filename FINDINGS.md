# 🧮 Math-Expression Parser & Evaluator — Full Cross-Language Report

**The same twelve parsing/evaluation strategies, implemented in C++, Haskell, and Python — to ask whether the C++ finding ("performance tracks memory allocation, not algorithmic cleverness") survives a change of runtime.**

</div>

> Detailed companion to the [README](README.md): all twelve strategies, grammar, build, the full cross-language analysis, and multi-core scaling.

---

This repo implements twelve ways to turn a string like `-2 ^ 2 + 3 * (4 - 1)` into `5`, in three languages that make very different memory trade-offs:

| | language | memory model | what we expect to change |
|---|---|---|---|
| [`cpp/`](cpp/) | C++26 | manual / RAII, arenas | baseline — allocation dominates |
| [`haskell/`](haskell/) | Haskell (GHC) | lazy, GC, persistent | laziness may hide or shift allocation |
| [`python/`](python/) | Python 3 | reference-counted, everything boxed | interpreter overhead may swamp the algorithm |

All three share **one grammar** and benchmark on **byte-identical corpora** (`bench/corpus/`, generated by [`bench/gen_corpus.py`](bench/gen_corpus.py)), so differences are language/algorithm, not input.

## The twelve strategies

`ast-recursive-descent`, `ast-shunting-yard`, `ast-pratt`, `ast-arena`, `multipass` (divide-and-conquer), `multipass-arena`, `multipass-bfs`, `multipass-reverse` (bottom-up), `direct-recursive-descent`, `direct-shunting-yard`, `direct-mp`, `bytecode-vm`.

See [`cpp/README.md`](cpp/README.md) for the full description of each and the in-depth C++ analysis.

## Grammar

Numbers, single-letter variables `a`–`z`, `+ - * / ^`, unary `+/-`, parentheses.
Precedence: `+ -` < `* /` < unary < `^` (right-associative). So `-2^2 = -4`, `2^3^2 = 512`.

## Build & run

```sh
python3 bench/gen_corpus.py        # generate shared corpora (once)

# C++  (needs GCC 14+ / Clang 17+ for <print>)
cmake -S cpp -B build -DCMAKE_BUILD_TYPE=Release -DCMAKE_CXX_COMPILER=g++-14
cmake --build build -j && ctest --test-dir build
./build/corpus_bench               # shared-corpus timing (cross-language comparable)

# Python  (3.10+)
python3 python/test_parsers.py     # correctness
python3 python/bench.py            # cross-check + timing

# Haskell  (GHC + cabal; needs libgmp — apt install libgmp-dev if linking fails)
cd haskell && cabal test && cabal run bench
```

`./build/corpus_bench`, `python/bench.py`, and `cabal run bench` all read the same
`bench/corpus/` files. (C++ also has `./build/bench` — its own generator — plus
`reeval`, `parallel_bench`, `single_par_bench`; see [`cpp/README.md`](cpp/README.md).)

### What survives the change of runtime, and what doesn't

The two big wins in C++ — *not building a tree* and *building it in a flat arena* —
are both **allocation/layout** effects, and **both are C++-only**. That single idea
explains every row below.

1. **In C++, memory layout dominates — flat beats pointer-chasing ~2.7×.** The
   fastest tier is everything *contiguous*: `direct-*` (no tree), `bytecode-vm`
   (flat opcode stream), and `ast-arena` (flat node buffer) all cluster at
   1.0–1.3. The pointer-walking forms — pointer-AST (`ast-*` ≈ 2.7) and `multipass`
   (3.5, down from 4.9 after iterator-passing eliminated per-call `candRange` binary
   searches) — lose by chasing `make_unique`'d nodes around the heap. Layout, not
   algorithm, sets the tiers.

2. **In managed runtimes that layout signal washes out.** Once the runtime boxes
   and GCs every node, contiguity is invisible: `ast-arena` is *no faster, even
   slightly slower* than pointer-AST in Python (1.3 vs 1.1) and Haskell (1.2 vs
   1.0), and "no tree" shrinks to a ~10–30% edge instead of C++'s 2.7×. Everything
   non-multipass lands within ~1.5×. **This is the headline: the C++ thesis was
   really about layout, and layout is exactly what managed runtimes hide.**

3. **The *top-down* multipass divide-and-conquer family loses in every language**
   — it does genuinely more work (repeated split-scans) to build the *same* tree,
   so no runtime rescues it. The sparse-table `multipass-bfs` is the cautionary
   tale: its O(n log n) RMQ precompute pays off **nowhere on these random
   corpora** — it's the *slowest* mp variant in Python (2.7) and Haskell (1.7)
   and loses to `multipass-arena` in C++ (2.2 vs 2.0). The precompute costs more
   than the cheap linear split-scan it replaces. (On structured mixed-precedence
   chains the RMQ finally beats its top-down siblings — but still loses to
   bottom-up; [see below](#where-bottom-up-provably-wins-mixed-precedence-chains).)
   The *bottom-up* member is the exception: `multipass-reverse` lands at
   **1.3–1.6 in all three languages** — best of the family in C++ and Python, a
   tie in Haskell, and in C++ it even beats every pointer-AST builder
   (1.6 vs 2.6–2.8).

4. **Overhead compresses the spread.** Fastest-to-slowest is ~3.5× in C++, but only
   ~1.7× in Haskell and ~2.7× in Python — GC, laziness, and interpreter overhead
   dominate, shrinking the gaps the algorithm creates. The more your runtime costs
   per operation, the less your algorithm choice shows.

### A reverse-multipass flavour

`multipass-reverse` inverts the divide-and-conquer: instead of finding the
lowest-precedence operator (the root) and splitting top-down, it reduces the
*tightest-binding* things first — deepest parens, then `^`, then `*/`, then `+-`
— agglomerating outward (one reduction pass per precedence level). Same tree,
opposite construction order. **Full explanation with diagrams:
[docs/multipass-reverse.md](docs/multipass-reverse.md).** Where does it land
among the multipass family?

ns/leaf at n=10000 on the neutral runner — **ranking only:**

| language | `multipass-reverse` | best *other* mp | fastest overall |
|---|--:|--:|--:|
| C++ | **114** ← dead tie for best of family | direct-mp 114 | direct-rd 76 |
| Python | **4 776** ← best of the mp family | direct-mp 8 608 | direct-rd 3 011 |
| Haskell | 2 466 ← ≈ tied | multipass 2 354 | ast-pratt 1 358 |

It's the **only multipass variant with no per-split scans** — the top-down
variants rescan candidates per split, and that compounds. After a rewrite of the
hot path (one shared item stack, segments folded right-to-left iteratively,
in-place level contraction — **~1.9× faster in C++, ~1.6× in Python** by
interleaved A/B), bottom-up now *wins the multipass family in C++ and Python*
and *roughly ties in Haskell*. In C++ it even beats every pointer-AST builder —
its arena output plus allocation-free parsing land it just behind `ast-arena`.
Note the contrast with `multipass-bfs`: both try to cut split cost, but reverse
does it by *never scanning for a split at all*, while bfs does it by *adding an
O(n log n) precompute* (and loses on random corpora). And, like every multipass
variant, neither beats the no-tree winners on the shared corpora.
(Regenerated on the neutral runner by the [CI bench](.github/workflows/bench.yml).)

### Where bottom-up provably wins: mixed-precedence chains

The shared corpora are random and balanced, so top-down splits land near the
middle. The structured inputs that separate the family attack its **two**
linear scans — top-down had two independent Θ(n²) holes, not one:

1. **The split scan** — a flat **product-of-powers chain**
   `3^2 * 2^2 / 2^2 * …` (powchain; think factored monomials) mixes `^`
   (prec 4) with `*` `/` (prec 2), defeating both fast paths at once: the
   flat-chain fold never applies (two precedences), and the right-to-left
   split scan never takes its prec-1 early exit (no `+`/`-`) — every split
   rescans its whole range. Quadratic for `multipass`, `multipass-arena`,
   `direct-mp`; the sparse-table `multipass-bfs` answers splits in O(1) and
   survives.
2. **The flat-chain *check*** — a long `^` run followed by a `*` run
   (`1^1^…^1 * 1 * 1 * …`, towerchain) leaves the same-precedence `^` prefix
   in the left sub-range after every right-end split, and the "is this range
   flat?" scan rereads it each time. Quadratic *even with O(1) splits* — this
   one catches `multipass-bfs` too.

Bottom-up `multipass-reverse` reduces each precedence level in one pass no
matter how the operators interleave: **Θ(n)** on both.

ns/leaf on the power chain, **before the fix below** (neutral 4-vCPU
GitHub runner; all three languages have since been patched):

| family member | C++ m=8192 | Python m=1024 | Haskell m=4096 |
|---|--:|--:|--:|
| top-down (`multipass` / `-arena` / `direct-mp`) | 3 236–4 864 | 52 368–53 140 | 9 757–10 943 |
| `multipass-bfs` (RMQ) | 84 | 13 709 | 3 010 |
| **`multipass-reverse`** | **43** | **3 135** | **1 302** |

That was **~8× (Haskell), ~17× (Python) and ~75–115× (C++) over top-down** at
the largest sizes measured — growing with n — and **~2–4× over the RMQ
variant** in every runtime. Note the three languages were measured at
*different* chain lengths (the column headers above), and a quadratic-vs-linear
gap grows with length, so the per-language ratios are **not cross-language
comparable** — at a common m the spread would be far narrower. The control
input — a single-precedence chain `1 + 2 - 3 + …`, where the flat-chain fold
does apply — keeps the whole family linear, confirming the blow-ups are about
*mixed precedence*, not chain length. The suite also runs the mirror-image
shape — `nestchain`, deep parenthesis nesting, the one construct where
*bottom-up* still recurses — so the adversarial testing points both ways;
`multipass-reverse` stays flat there too.
`./build/adversarial_bench`, `python3 python/adversarial.py`, and
`cabal run adversarial` rerun these shapes — but the shipped top-down variants
now include the fix below, so expect the post-fix ~2–4× gaps, **not** this
table: the pre-fix numbers above are preserved from the last CI run before the
fix and cannot be regenerated from the current sources.

### The fix: bounded scans + precedence buckets

Both holes have the same cure, applied to the top-down variants in **all
three languages**: each linear scan is **bounded at 16 candidates**, and past
the budget the answer comes from per-depth **sorted position arrays, one per
precedence class** (`+ -` / `* /` / `^` / unary), by binary search — the
rightmost prec-1 in range, else the rightmost prec-2, else the range's first
candidate; flatness is "exactly one non-unary class present in range". Common
ranges resolve inside the budget on the unchanged fast path; adversarial
chains drop from Θ(n²) to **O(n log n)**. `multipass-arena` in C++
additionally answers both questions with a single AVX2 compare over a
per-depth precedence byte array (runtime-dispatched, scalar fallback) — worth
another ~5–10 % on the random corpus. In Haskell the buckets only materialise
if a budget is ever exceeded — laziness for free. Python — where per-split
bisect overhead is itself expensive — goes one step further: when the budget
trips, it folds the **whole precedence level** in one pass over the bucket
slice (left-assoc level folds build the same tree as repeated rightmost
splits), and the flat check is a precomputed O(1) "next class change" lookup
instead of any scan at all.

A complementary fix closes the per-call binary-search overhead on the **random
corpus**: `multipass` (C++) previously recomputed candidate sub-range boundaries
with `candRange(lo, hi, d)` (O(log n)) on every recursive entry. Passing the
`(cbeg, cend)` iterator slice directly makes sub-range splits O(1) — no search
at all. This alone cuts the random-corpus ratio from **4.9× → 3.5×** for
`multipass` on the neutral runner (−29 % at n=1000). The same AVX2 SIMD flat/split
check is also wired into `direct-mp`, but the random corpus rarely exercises long
flat chains so the gain is within noise there.

Effect at m=8192, ns/leaf on the **neutral 4-vCPU GitHub runner** (before =
the last pre-fix CI run, after = the latest CI run; every "after" cell is flat
or falling across m=512/2048/8192 — no quadratic growth; individual cells
wobble run to run on the shared VM):

| | powchain before → after | towerchain after † |
|---|--:|--:|
| `multipass` | 3 791 → **146** | 145 |
| `multipass-arena` | 4 864 → **83** | 80 |
| `direct-mp` | 3 236 → **69** | 68 |
| `multipass-bfs` | 84 → 86 (splits were already O(1)) | **89** |
| `multipass-reverse` (unchanged) | 43 → 41 | 40 |

† towerchain landed in the same push as the fix, so it has no pre-fix CI run.
On the discovery laptop it measured 2 947 ns/leaf for `multipass-bfs` and
8 000–11 000 for the other top-down variants before the fix — versus the flat
~55–130 above after it.

Top-down C++ is now *linear* on its own worst case — `multipass-arena` and
`direct-mp` land within **~1.7–2× of bottom-up** instead of ~80–115×, and
**beat `multipass-bfs`** without its sparse table. On the new nestchain shape
(deep parentheses — bottom-up's own worst case) `multipass-reverse` stays flat
at 62–67 ns/leaf across all sizes, within ~4 % of `ast-arena`, while the
top-down family starts 2–3.8× above it at m=512 and only converges by m=8192.
The structural distinction stands:
`multipass-reverse` needs no budget, no buckets and no fallback, because it
never asks a question whose answer lies elsewhere in the range. The random
corpus is unaffected (deltas below the laptop's ±15 % noise floor — the two
quadratic inputs needed an adversarial bench to find precisely because random
expressions never trigger them).

The **Python and Haskell ports** close the same holes the same way. Before the
port, their towerchain climbed ~3× per 4× length on the neutral runner (Python
top-down 61 000–62 000 ns/leaf at m=1024 with `multipass-bfs` at 27 873;
Haskell 14 700–17 500 at m=4096 with bfs at 6 118 — versus flat 3 243 / 1 435
for `multipass-reverse`); after it, both chains are flat on the neutral runner
too (CI run 27417707827): Python towerchain 3 700–8 100 ns/leaf across sizes
and strategies, vs 3 300–6 100 for sumchain — same tier; Haskell 1 200–2 600
vs 900–1 400 for sumchain. (`multipass-bfs` is 30–40 % above the other
top-down forms on both adversarial shapes in both languages — its sparse-table
build overhead shows through — but the growth is flat, not quadratic.)

## Multi-core scaling

Does more cores change any of this? Batch throughput on a **neutral GitHub runner
(4 vCPU)**, corpus split across W workers (regenerated by the
[bench workflow](.github/workflows/bench.yml)). Short answer: **the per-expression
ranking is core-count-invariant — the only thing that depends on cores is the
language's parallelism model.**

**C++** (`std::thread`) — identical ranking at W=1/2/4, ~2.7–2.9× speedup at W=4:

| strategy | ns/leaf W=1 | W=4 | speedup@4 | eff |
|---|--:|--:|--:|--:|
| direct-recursive-descent | 66 | 25 | 2.69× | 0.67 |
| ast-arena | 83 | 28 | 2.93× | 0.73 |
| multipass-reverse | 106 | 36 | 2.92× | 0.73 |
| multipass | 247 | 92 | 2.69× | 0.67 |

Per-strategy *efficiency* differences are **within run-to-run noise** on this
shared 4-vCPU VM — across six runs `ast-arena` ranged 0.80 → 0.57 → 0.55 → 0.53
→ 0.68 → 0.73, so it is **not** the case that any strategy reliably scales
better or that multi-core amplifies the allocation gap. The same goes for the
*aggregate* speedup band: ~2.1–2.9× depending on the run. The robust facts are
only the **invariant ranking** and the ~0.5–0.75 efficiency band. The full
eight-AST-builder W=1-vs-W=4 ranking (it doesn't move) is in the
[README](README.md#and-the-same-comparison-at-4-cores).

**Haskell** (`-threaded` + `setNumCapabilities`) — every strategy ~2.4–2.5× at W=4
this run (~2.0–2.8× across runs — same VM noise); no GIL.

**Python** — scales with **processes** (~2.2–2.4× this run, ~1.9–2.5× across
runs) but **not threads** — a live GIL demo:

| pool | speedup@4 |
|---|--:|
| process | 1.9–2.5× across runs ✓ |
| thread | 0.87–1.0× ✗ (flat; 0.93–0.98× this run) |

So cores only *multiply* throughput, and only where the runtime allows true
parallelism (C++/Haskell threads; Python processes, never threads). 8-core
scaling would need real hardware — GH runners are ~4 shared vCPUs.

## Compile once, evaluate many

The one-shot verdict ("don't build a tree") **inverts** when you evaluate the same
expression repeatedly with different variable values: build a reusable compiled
form once, and the parse amortizes away. Shared variable corpus (`vars_n*.txt`),
per-eval ns/expr at n=1000, neutral runner:

| compiled form | C++ | Python | Haskell |
|---|--:|--:|--:|
| ast-ptr (pointer AST) | 27k | **280k** | **35k** |
| ast-arena | 26k | 322k | 43k |
| multipass-arena | 26k | 337k | 45k |
| rpn | **18k** | — | — |
| bytecode | 19k | 290k | 56k |
| **reparse-rd** (re-parse each eval) | 186k | 2.90M | 936k |

Two findings:

1. **Building any reusable form beats re-parsing by ~7–26×**, and break-even is
   tiny (≲ 5 evals in every language — usually ~1). So if you evaluate more than
   a couple of times, *build the structure* — the opposite of the one-shot result.
2. **The best compiled form is runtime-specific:**
   - **C++** → flat (`rpn`/`bytecode`), and the three tree forms cluster
     (26–27k) — memory layout wins.
   - **Python** → pointer-AST and `bytecode` trade places run to run (this run:
     ast-ptr 280k < bytecode 290k; earlier runs flipped) — the robust fact is
     both beat the arena forms, whose extra indirection costs more than it saves
     in a boxed runtime.
   - **Haskell** → **an AST** — pointer `Expr` and arena trade places run to run
     (this run: pointer 35k < arena 43k; the previous run flipped); the robust
     fact is that flat `bytecode` is the one form that *doesn't* win there
     (GHC's pattern-matching tree walk beats a list-based VM).

   So *which* tree/representation to build depends on the language — but *that* you
   should build one (when eval-many) is universal.

(Benches: `cpp/bench/corpus_reeval.cpp`, `python/reeval.py`, `haskell/app/Reeval.hs`;
regenerated by the [bench workflow](.github/workflows/bench.yml).)
