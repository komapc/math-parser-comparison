# 🧮 Math-Expression Parser & Evaluator — Full Cross-Language Report

**The same fifteen parsing/evaluation strategies in C++, Rust, Haskell, and Python.**

</div>

> Detailed companion to the [README](README.md).

| | language | memory model |
|---|---|---|
| [`cpp/`](cpp/) | C++26 | manual / RAII, arenas |
| [`rust/`](rust/) | Rust (LLVM) | ownership, arenas; one `unsafe` block |
| [`haskell/`](haskell/) | Haskell (GHC) | lazy, GC, persistent |
| [`python/`](python/) | Python 3 | reference-counted, everything boxed |

All three share **one grammar** and benchmark on **byte-identical corpora**
(`bench/corpus/`, generated by [`bench/gen_corpus.py`](bench/gen_corpus.py)).

## The fifteen strategies

`ast-recursive-descent`, `ast-shunting-yard`, `ast-pratt`, `ast-arena`,
`multipass` (top-down divide-and-conquer), `multipass-arena`, `multipass-bfs`,
`multipass-reverse` (bottom-up), `multipass-reverse-fold` (bottom-up, fused),
`direct-recursive-descent`, `direct-shunting-yard`, `direct-reverse`,
`direct-mp`, `bytecode-vm`, and `direct-scannerless` — recursive descent with
the lexer fused in, the control row for what the shared lexer costs (see
[Lexing rules](#lexing-rules--applied-to-every-parser)).
Full per-strategy descriptions: [`cpp/README.md`](cpp/README.md).

## Grammar

Numbers, single-letter variables `a`–`z`, `+ - * / ^`, unary `+/-`, parentheses.
Precedence: `+ -` < `* /` < unary < `^` (right-associative). So `-2^2 = -4`, `2^3^2 = 512`.

## Build & run

```sh
python3 bench/gen_corpus.py        # generate shared corpora (once)

# C++  (needs GCC 14+ / Clang 17+ for <print>)
cmake -S cpp -B build -DCMAKE_BUILD_TYPE=Release -DCMAKE_CXX_COMPILER=g++-14
cmake --build build -j && ctest --test-dir build
./build/corpus_bench               # shared-corpus timing (cross-language comparable)

# Rust  (stable toolchain)
cd rust && cargo test --release && cargo run --release --bin bench

# Python  (3.10+)
python3 python/test_parsers.py && python3 python/test_fuzz.py
python3 python/bench.py

# Haskell  (GHC + cabal; needs libgmp — apt install libgmp-dev if linking fails)
cd haskell && cabal test && cabal run bench
```

Correctness is enforced two ways: curated spec suites in each language (the
same cases, including IEEE corners and literal overflow → `inf`/`0`), plus
differential fuzzing in C++, Rust and Python ([C++](cpp/tests/fuzz_differential.cpp)
· [Rust](rust/tests/fuzz.rs) · [Python](python/test_fuzz.py)) — all fifteen strategies must agree, value or
rejection, on 3 000 random + 3 000 mutated inputs per run. Haskell has the
spec suite only.

Raw fastest, median ns/leaf: **C++ ≈ 49** (`direct-reverse`, with

terms. The lexer-free control sits at 39 / 35 / 412 / 1 935.

### What survives the change of runtime

1. **In C++, memory layout dominates.** Everything *contiguous* — `direct-*`
   (no tree), `bytecode-vm`, `ast-arena`, the fused reducer — clusters at
   1.0–1.4; every pointer-walking form pays ~2.6× for chasing `make_unique`'d
   nodes. Rust reproduces the C++ tiers almost line for line — same
   clusters, same ratios — under a different compiler (LLVM), so the tiers
   are the memory model's, not GCC's. Where the two differ is the top-down
   family (the Rust port has no SIMD candidate scan, so `multipass-arena` /
   `direct-mp` sit at 3.3–3.7× instead of 2.2–2.7×) and the fused reducer's
   sliver over `ast-arena`, which LLVM does not reproduce.
2. **Managed runtimes hide layout.** Boxed/GC'd nodes make contiguity
   invisible: `ast-arena` is *slower* than pointer-AST in Python and Haskell,
   and "no tree" shrinks to a 20–30 % edge in Python and vanishes in Haskell,
   where `ast-pratt` is the fastest strategy outright.
3. **Top-down multipass loses in every language** — repeated split-scans are
   real extra work no runtime rescues. `multipass-bfs`'s RMQ precompute pays
   off nowhere on random corpora. The bottom-up member is the exception — see
   below.
4. **Overhead compresses the spread:** fastest-to-slowest is ~5× in C++ and
   Rust but ~3× in Haskell and Python. (Haskell read ~1.7× until the number-parsing
   fix below removed a constant term from every strategy.)

## Lexing rules — applied to every parser

Every strategy shares one lexer per language so that the tables measure the
parsing approach, not incidental lexing differences. Writing the shortest
correct evaluator (under thirty lines of C++) and then making it fast and
strict surfaced three rules about that lexer — and a rule that helps one
strategy is applied to all of them or to none.

**1. Parse numbers on the fast path.** Number conversion, not whitespace or
dispatch, is the dominant per-leaf cost: the draft went from `strtod` to
`std::from_chars` and got ~40 % faster. The C++ lexer already did this;
Python's `float()` is the same fast path. Haskell's lexer used
`reads :: Double`, which goes through `Rational` — roughly two-thirds of the
fastest Haskell strategies' time. It now takes Clinger's fast path first (a
mantissa of ≤15 digits times an exact power of ten up to 10²² is one
correctly rounded IEEE operation, bit-identical to `reads`; verified on 27
literals including `1e22`, `1e23`, `4.9e-324`, `1e400`), falling back to
`reads` for anything longer. Neutral runner, ns/leaf, median over the four
sizes, median of three CI runs before and after:

| Haskell strategy | before | after | × |
|---|--:|--:|--:|
| ast-recursive-descent | 1 392 | 504 | 2.8 |
| ast-pratt | 1 403 | 480 | 2.9 |
| ast-arena | 1 669 | 686 | 2.4 |
| multipass | 1 888 | 993 | 1.9 |
| multipass-bfs | 2 320 | 1 441 | 1.6 |
| multipass-reverse-fold | 1 702 | 768 | 2.2 |
| direct-recursive-descent | 1 458 | 522 | 2.8 |
| direct-reverse | 1 438 | 536 | 2.7 |
| bytecode-vm | 1 526 | 597 | 2.6 |

Same tiers, 1.6–2.9× less time — the earlier Haskell columns were largely
measuring `reads`. Two things the constant term had hidden: the arena forms'
penalty against the pointer classics is ~1.5–1.7×, not ~1.3×, and the
Haskell spread is ~3×, the same as Python's.

**2. Don't materialise what the algorithm never indexes.** Any extra pass
over the input — even a one-line whitespace strip — costs more than it saves,
and a token array is the biggest such pass. The shared C++ lexer therefore
has two modes over one set of rules: `Lexer::next()` streams one token at a
time, `tokenize()` builds the array by calling it. Every strategy that reads
its input left to right with bounded lookahead streams — the classics,
`ast-arena`, `direct-*`, `bytecode-vm`, and the fused reducer (one token of
lookahead). The divide-and-conquer family and the buffered `multipass-reverse`
keep the array because their algorithms index it — a property of those
algorithms, honestly paid — and for them the token shrank from 24 to 16
bytes. Neutral runner, ns/leaf, median over the four sizes, median of three
CI runs before and after:

| C++ strategy | tokens | before | after | Δ |
|---|---|--:|--:|--:|
| ast-recursive-descent | stream | 179 | 127 | −29 % |
| ast-shunting-yard | stream | 187 | 129 | −31 % |
| ast-pratt | stream | 178 | 130 | −27 % |
| ast-arena | stream | 85 | 72 | −16 % |
| multipass-reverse-fold | stream | 83 | 68 | −18 % |
| direct-recursive-descent | stream | 67 | 50 | −25 % |
| direct-shunting-yard | stream | 74 | 49 | −33 % |
| direct-reverse | stream | 66 | 50 | −25 % |
| bytecode-vm | stream | 86 | 59 | −31 % |
| multipass | array | 235 | 235 | 0 % |
| multipass-arena | array | 135 | 130 | −4 % |
| direct-mp | array | 110 | 107 | −3 % |
| multipass-bfs | array | 150 | 156 | +4 % |
| multipass-reverse | array | 108 | 99 | −8 % |

The token array was 16–33 % of every streaming strategy's time; the 16-byte
token is worth a few per cent at most for the array-bound ones. The ranking
inside each tier is unchanged, but two earlier claims moved: the C++ no-tree
tier is now a three-way tie at ~50 ns/leaf, and the fused reducer's nestchain
lead over `ast-arena` shrank from ~0.6× to ~0.8× because `ast-arena` no
longer pays for a token per parenthesis.

Python keeps its token list: a generator-based stream is a wash there
(0.93–1.05× across six pinned runs) — the interpreter's per-token dispatch
dominates whichever way the tokens arrive. Haskell's token list is lazy and
already fuses with its consumer.

**3. Measure the lexer, don't guess it.** `direct-scannerless` is
`direct-recursive-descent` with the lexer fused into the grammar: each rule
compares the next *character* against the one or two it can accept, and
whitespace is consumed exactly once, right after each token. It obeys the same
lexical rules as the shared lexer and passes the same spec and fuzz suites. It
is not a new parsing algorithm; it is the control row that turns "the lexer
is expensive" into a number per language (ns/leaf, median over sizes and
runs; the ratio's range is over the three runs):

| | `direct-rd` | `direct-scannerless` | control ÷ `direct-rd` |
|---|--:|--:|--:|
| C++ | 50 | 39 | 0.78 (0.75–0.80) |
| Rust | 52 | 35 | 0.69 (0.64–0.70) |
| Python | 2 898 | 1 935 | 0.67 (0.65–0.75) |
| Haskell | 476 | 412 | 0.87 (0.82–0.96) |

C++ pays a fifth of `direct-rd`'s time for having a lexer at all, Rust and
Python a third; in Haskell the control buys ~13 % and the range touches
run-to-run noise. The remaining gap is context: after an operand the fused
parser tests only operator characters, where a general lexer classifies the
character first. That is intrinsic to having a lexer, and it is the ceiling
on what rule 2 can recover.

## `multipass-reverse` — the two results

Bottom-up construction: reduce the tightest-binding constructs first, one
in-place sweep per precedence level; no split search, recursion only per paren
group. Same tree, opposite order. **Algorithm walk-through:
[docs/multipass-reverse.md](docs/multipass-reverse.md).**

### Result 1 — vs the classics: competitive — narrowly ahead in C++ and Python

ns/leaf at n=10000, neutral runner:

| language | `multipass-reverse-fold` | `multipass-reverse` | fastest classic tree builder | fastest overall |
|---|--:|--:|--:|--:|
| C++ | **67** | 100 | ast-arena 69 | direct-reverse 49 (direct-rd 50, tie) |
| Rust | 72 | 102 | **ast-arena 71** (tie) | direct-rd / direct-reverse 52 (tie) |
| Python | **3 512** | 4 846 | ast-sy 3 706 | direct-reverse 2 701 |
| Haskell | 999 | 1 712 | ast-pratt 580 | direct-reverse 551 |

(The lexer-free control `direct-scannerless` sits at 39 / 36 / 1 929 / 564.)

The fused form is the fastest tree builder in C++ and Python (~2–5 % ahead
of `ast-arena` in C++, −1…+8 % against the best pointer classic in Python;
positive in 11 of 12 size×run measurements in each language across three
independent CI runs — a consistent sliver, not a margin). In Rust it is a
tie: 0–2 % *behind* `ast-arena` in all 12 measurements, so LLVM does not
reproduce GCC's sliver. Its no-tree twin `direct-reverse` is genuinely
faster in Python (~10–13 % over `direct-sy`, ~7–21 % over `direct-rd`,
repeated across runs), but in C++ it is a **three-way tie** with
`direct-recursive-descent` and `direct-shunting-yard` at ~50 ns/leaf
(+0…+3 % and −1…+5 % across runs), and in Rust a tie with `direct-rd`
(−5…+2 %) that is 7–10 % ahead of `direct-sy`. Haskell is the exception: the
pointer classics lead every arena form by ~1.5–1.7×, and `direct-reverse` vs
`direct-rd` swings −11…+18 % run to run (a tie, noisily). The buffered
`multipass-reverse` — the pedagogical version — trails its fused form by
~1.3–1.5×. Design of the fused form:
[docs/multipass-reverse.md](docs/multipass-reverse.md#the-fused-variant).

### Result 2 — vs its family: strictly better

The top-down variants answer "where is the loosest operator in this range?" by
scanning. Two structured inputs make that quadratic:

1. **powchain** `3^2 * 2^2 / 2^2 * …` (factored monomials) — mixes `^` with
   `* /`, defeating both the flat-chain fold and the prec-1 early exit: every
   split rescans its range. Θ(n²) for `multipass`/`-arena`/`direct-mp`;
   `multipass-bfs`'s O(1) RMQ splits survive.
2. **towerchain** `1^1^…^1 * 1 * …` — the "is this range flat?" check rereads
   the `^` prefix after every split. Θ(n²) *even with O(1) splits* — catches
   `multipass-bfs` too.

`multipass-reverse` never asks the question: **Θ(n) on both.** A
single-precedence control chain (sumchain) keeps the whole family linear,
isolating *mixed precedence* as the trigger; a fourth shape (**nestchain**,
deep parentheses — the one construct where bottom-up recurses) attacks
reverse's own worst case, and it stays flat there too (66 ns/leaf across
sizes; `ast-arena` sits at 39); the fused form is the fastest tree builder on
that shape outright (33 vs `ast-arena` 50 at m=8192).

Pre-fix, powchain (last CI run before the top-down family was patched; sizes
differ per language and the gap grows with size, so ratios are not
cross-language comparable):

| family member | C++ m=8192 | Python m=1024 | Haskell m=4096 |
|---|--:|--:|--:|
| top-down (`multipass` / `-arena` / `direct-mp`) | 3 236–4 864 | 52 368–53 140 | 9 757–10 943 |
| `multipass-bfs` (RMQ) | 84 | 13 709 | 3 010 |
| **`multipass-reverse`** | **43** | **3 135** | **1 302** |

**The fix** (applied to the top-down variants in all four languages): every
linear scan is bounded at 16 candidates; past the budget, per-depth sorted
position arrays per precedence class answer splits by binary search — Θ(n²)
drops to O(n log n). `multipass-arena`/`direct-mp` in C++ additionally use an
AVX2 flat/split check; Python and Rust fold whole precedence levels on budget trip;
Haskell materialises buckets lazily. Effect at m=8192 (ns/leaf, neutral
runner; "after" cells are flat across sizes — no quadratic growth):

| | powchain before → after | towerchain after † |
|---|--:|--:|
| `multipass` | 3 791 → **151** | 160 |
| `multipass-arena` | 4 864 → **86** | 83 |
| `direct-mp` | 3 236 → **70** | 71 |
| `multipass-bfs` | 84 → 87 (splits were already O(1)) | **90** |
| `multipass-reverse` (unchanged) | 43 → 40 | 43 |
| `multipass-reverse-fold` | — → **30** | **34** |

† towerchain landed with the fix, so it has no pre-fix CI run (discovery-laptop
pre-fix: ~2 900–11 000 ns/leaf). The Python and Haskell ports close the same
holes the same way; their adversarial chains are flat on the neutral runner too.

So: the rest of the family is linear now — **because it was rescued**, with
budgets, buckets and SIMD, and it still trails bottom-up by 1.7–3.8× (2.3–5×
against the fused form). `multipass-reverse` is **the only member of the
family whose worst case is its average case**: same two columns, same code,
no machinery. The pre-fix numbers are preserved from CI and cannot be
regenerated from current sources; the shipped binaries reproduce the "after"
column (`./build/adversarial_bench`, `python3 python/adversarial.py`,
`cabal run adversarial`).
