# 🧮 Math-Expression Parser & Evaluator — Full Cross-Language Report

**The same twelve parsing/evaluation strategies in C++, Haskell, and Python — to ask whether the C++ finding ("performance tracks memory allocation, not algorithmic cleverness") survives a change of runtime.**

</div>

> Detailed companion to the [README](README.md).

| | language | memory model |
|---|---|---|
| [`cpp/`](cpp/) | C++26 | manual / RAII, arenas |
| [`haskell/`](haskell/) | Haskell (GHC) | lazy, GC, persistent |
| [`python/`](python/) | Python 3 | reference-counted, everything boxed |

All three share **one grammar** and benchmark on **byte-identical corpora**
(`bench/corpus/`, generated by [`bench/gen_corpus.py`](bench/gen_corpus.py)).

## The twelve strategies

`ast-recursive-descent`, `ast-shunting-yard`, `ast-pratt`, `ast-arena`,
`multipass` (top-down divide-and-conquer), `multipass-arena`, `multipass-bfs`,
`multipass-reverse` (bottom-up), `direct-recursive-descent`,
`direct-shunting-yard`, `direct-mp`, `bytecode-vm`.
Full per-strategy descriptions: [`cpp/README.md`](cpp/README.md).

## Grammar

Numbers, single-letter variables `a`–`z`, `+ - * / ^`, unary `+/-`, parentheses.
Precedence: `+ -` < `* /` < unary < `^` (right-associative). So `-2^2 = -4`, `2^3^2 = 512`.

## Build & run

```sh
python3 bench/gen_corpus.py        # generate shared corpora (once)

# C++  (needs GCC 14+ / Clang 17+ for <print>)
cmake -S cpp -B build -DCMAKE_BUILD_TYPE=Release -DCMAKE_CXX_COMPILER=g++-14
cmake --build build -j && ctest --test-dir build
./build/corpus_bench               # shared-corpus timing (cross-language comparable)

# Python  (3.10+)
python3 python/test_parsers.py && python3 python/test_fuzz.py
python3 python/bench.py

# Haskell  (GHC + cabal; needs libgmp — apt install libgmp-dev if linking fails)
cd haskell && cabal test && cabal run bench
```

Correctness is enforced two ways: curated spec suites in each language, plus
differential fuzzing ([C++](cpp/tests/fuzz_differential.cpp) ·
[Python](python/test_fuzz.py)) — all twelve strategies must agree, value or
rejection, on 3 000 random + 3 000 mutated inputs per run.

Raw fastest, median ns/leaf: **C++ ≈ 66**, **Haskell ≈ 1 290**, **Python ≈ 2 930**
— C++ is ~20–44× faster absolute; Python and Haskell land within ~2.5×.

### What survives the change of runtime

1. **In C++, memory layout dominates.** Everything *contiguous* — `direct-*`
   (no tree), `bytecode-vm`, `ast-arena` — clusters at 1.0–1.3; every
   pointer-walking form pays ~2.6–2.8× for chasing `make_unique`'d nodes.
2. **Managed runtimes hide layout.** Boxed/GC'd nodes make contiguity
   invisible: `ast-arena` is *slower* than pointer-AST in Python and Haskell,
   and "no tree" shrinks to a 10–30 % edge. **The C++ thesis was really about
   layout, and layout is exactly what managed runtimes hide.**
3. **Top-down multipass loses in every language** — repeated split-scans are
   real extra work no runtime rescues. `multipass-bfs`'s RMQ precompute pays
   off nowhere on random corpora (slowest mp variant in Python and Haskell).
   The bottom-up member is the exception — see below.
4. **Overhead compresses the spread:** fastest-to-slowest is ~3.5× in C++ but
   only ~1.7× (Haskell) / ~2.7× (Python).

## `multipass-reverse` — the two results

Bottom-up construction: reduce the tightest-binding constructs first, one
in-place sweep per precedence level; no split search, recursion only per paren
group. Same tree, opposite order. **Algorithm walk-through:
[docs/multipass-reverse.md](docs/multipass-reverse.md).**

### Result 1 — vs the classics: competitive

ns/leaf at n=10000, neutral runner:

| language | `multipass-reverse` | best *other* mp | fastest overall |
|---|--:|--:|--:|
| C++ | **114** ← dead tie for best of family | direct-mp 114 | direct-rd 76 |
| Python | **4 776** ← best of the mp family | direct-mp 8 608 | direct-rd 3 011 |
| Haskell | 2 466 ← ≈ tied | multipass 2 354 | ast-pratt 1 358 |

Second-fastest tree builder of eight in C++ (behind only `ast-arena`, which
shares its arena layout), ahead of every pointer-AST classic; ~1.3× behind the
classics in the managed runtimes, where the layout advantage evaporates. A
novel construction landing within ~18 % of the best-tuned classic on its home
turf — competitive, not faster, and the tables say so.

### Result 2 — vs its family: strictly better

The top-down variants answer "where is the loosest operator in this range?" by
scanning. Two structured inputs make that quadratic:

1. **powchain** `3^2 * 2^2 / 2^2 * …` (factored monomials) — mixes `^` with
   `* /`, defeating both the flat-chain fold and the prec-1 early exit: every
   split rescans its range. Θ(n²) for `multipass`/`-arena`/`direct-mp`;
   `multipass-bfs`'s O(1) RMQ splits survive.
2. **towerchain** `1^1^…^1 * 1 * …` — the "is this range flat?" check rereads
   the `^` prefix after every split. Θ(n²) *even with O(1) splits* — catches
   `multipass-bfs` too.

`multipass-reverse` never asks the question: **Θ(n) on both.** A
single-precedence control chain (sumchain) keeps the whole family linear,
isolating *mixed precedence* as the trigger; a fourth shape (**nestchain**,
deep parentheses — the one construct where bottom-up recurses) attacks
reverse's own worst case, and it stays flat there too (62–67 ns/leaf across
sizes, within ~4 % of `ast-arena`).

Pre-fix, powchain (last CI run before the top-down family was patched; sizes
differ per language and the gap grows with size, so ratios are not
cross-language comparable):

| family member | C++ m=8192 | Python m=1024 | Haskell m=4096 |
|---|--:|--:|--:|
| top-down (`multipass` / `-arena` / `direct-mp`) | 3 236–4 864 | 52 368–53 140 | 9 757–10 943 |
| `multipass-bfs` (RMQ) | 84 | 13 709 | 3 010 |
| **`multipass-reverse`** | **43** | **3 135** | **1 302** |

**The fix** (applied to the top-down variants in all three languages): every
linear scan is bounded at 16 candidates; past the budget, per-depth sorted
position arrays per precedence class answer splits by binary search — Θ(n²)
drops to O(n log n). `multipass-arena`/`direct-mp` in C++ additionally use an
AVX2 flat/split check; Python folds whole precedence levels on budget trip;
Haskell materialises buckets lazily. An iterator-passing fix also cut
`multipass`'s random-corpus ratio 4.9× → 3.5×. Effect at m=8192 (ns/leaf,
neutral runner; "after" cells are flat across sizes — no quadratic growth;
individual cells wobble run to run):

| | powchain before → after | towerchain after † |
|---|--:|--:|
| `multipass` | 3 791 → **146** | 145 |
| `multipass-arena` | 4 864 → **83** | 80 |
| `direct-mp` | 3 236 → **69** | 68 |
| `multipass-bfs` | 84 → 86 (splits were already O(1)) | **89** |
| `multipass-reverse` (unchanged) | 43 → 41 | 40 |

† towerchain landed with the fix, so it has no pre-fix CI run (discovery-laptop
pre-fix: ~2 900–11 000 ns/leaf). The Python and Haskell ports close the same
holes the same way; their adversarial chains are flat on the neutral runner too.

So: the rest of the family is linear now — **because it was rescued**, with
budgets, buckets and SIMD, and it still trails bottom-up by 1.7–3.6×.
`multipass-reverse` is **the only member of the family whose worst case is its
average case**: same two columns, same code, no machinery — it never asks a
question whose answer lies elsewhere in the range. The pre-fix numbers are
preserved from CI and cannot be regenerated from current sources; the shipped
binaries reproduce the "after" column
(`./build/adversarial_bench`, `python3 python/adversarial.py`,
`cabal run adversarial`).

Per-language detail: [`cpp/`](cpp/README.md) · [`python/`](python/README.md) · [`haskell/`](haskell/README.md).

## Multi-core scaling

Batch throughput, corpus split across W workers, neutral 4-vCPU runner.
**The ranking is core-count-invariant** — only the runtime's parallelism model
matters. C++ (`std::thread`) ~2.7–2.9× at W=4 this run; Haskell (`-threaded`)
~2.4–2.5×; Python **processes** ~2.2–2.4× but **threads 0.93–0.98× — flat, the
GIL live**. Bands across runs: ~1.9–2.9×; per-strategy efficiency differences
are VM noise (across six runs `ast-arena`'s efficiency spanned 0.53–0.80), so
no strategy reliably scales better and multi-core does not amplify the
allocation gap. Real 8-core scaling needs dedicated hardware.

## Compile once, evaluate many

The one-shot verdict ("don't build a tree") **inverts** when the same
expression is evaluated repeatedly with different variable values. Per-eval
ns/expr at n=1000, neutral runner:

| compiled form | C++ | Python | Haskell |
|---|--:|--:|--:|
| ast-ptr (pointer AST) | 27k | **280k** | **35k** |
| ast-arena | 26k | 322k | 43k |
| multipass-arena | 26k | 337k | 45k |
| rpn | **18k** | — | — |
| bytecode | 19k | 290k | 56k |
| **reparse-rd** (re-parse each eval) | 186k | 2.90M | 936k |

1. **Any reusable form beats re-parsing ~7–26×**; break-even ≲ 5 evals,
   usually ~1.
2. **The best form is runtime-specific:** flat (`rpn`/`bytecode`) in C++;
   pointer-AST vs bytecode is a run-to-run coin flip in Python (both beat the
   arena forms); an AST in Haskell, where flat bytecode is the one form that
   *loses* (GHC's pattern-matching tree walk beats a list-based VM). *Which*
   structure to build is language-specific — *that* you should build one is
   universal.
